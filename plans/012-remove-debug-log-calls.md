## Why this matters

Two `android.util.Log.d("TimelineDebug", ...)` calls run on every timeline view and every save action, logging the dates the user is viewing (and the refresh trigger value) to system logcat. For a personal-journal app whose product brief stresses "本地应用...面向你个人内心" (local, personal, inner — see `MY_ORIGIN_GOAL.md:19`), this is a data-minimization leak: any app holding the `READ_LOGS` permission on the device can read the user's viewing patterns. It is also pure noise in production logcat. The calls were debug scaffolding during development and carry no production value — the same info is available via the ViewModel state for debugging via Android Studio.

## Current state

### `app/src/main/java/com/shijiben/data/repository/EventRepository.kt`

Role: Repository wrapping `EventDao`. The log call is at line 18, inside `getEventsByDate` which is invoked on every timeline view and date change:

```kotlin
fun getEventsByDate(year: Int, month: Int, day: Int): Flow<List<EventEntity>> {
    val (start, end) = dayRange(year, month, day)
    android.util.Log.d("TimelineDebug", "[EventRepository] getEventsByDate: y=$year m=$month d=$day, start=$start, end=$end")
    return eventDao.getEventsByDate(start, end)
}
```

### `app/src/main/java/com/shijiben/feature/timeline/TimelineViewModel.kt`

Role: ViewModel for `TimelineScreen`. The log call is at line 73, inside `refresh()` which is called after every event/note save:

```kotlin
fun refresh() {
    android.util.Log.d("TimelineDebug", "[TimelineViewModel] refresh() called, current viewingDate=${_viewingDate.value}, trigger=${_refreshTrigger.value}")
    _refreshTrigger.value = _refreshTrigger.value + 1
}
```

### Repo conventions to match

- **No logger wrapper exists.** Kotlin's `android.util.Log` is referenced inline (no import needed — the `android.util.` prefix is used at every call site). Match this style; do NOT introduce a `Logger` interface for this plan.
- **`BuildConfig.DEBUG`** is generated by the Android Gradle Plugin by default (`BuildConfig` is accessible from any module source set). It is `true` in debug builds, `false` in release. If you keep any debug log, gate it on `BuildConfig.DEBUG` — but this plan deletes the calls entirely.
- **No tests assert on log output.** Verified: the test tree under `app/src/test/` references no `Log.d` output. Safe to delete.

## Maintenance notes

- **If future debugging needs these logs back**, prefer `if (BuildConfig.DEBUG) android.util.Log.d(...)` over an unconditional call, and prefer scoping the tag to a single `com.shijiben` namespace. The data-minimization concern is about *unconditional* logging of user-viewed dates in release builds.
- **A lint rule** (`detekt` or Android `lint` with `LogConditional` / a custom `LogUsage` rule) would prevent this class of leak at the source. That is finding DX-02 (lint config), deferred from this batch — a reviewer landing DX-02 should consider banning `android.util.Log` outside a thin wrapper.
