## Context

当前首页 (`HomeScreen.kt`) 采用线性布局，所有事件按添加顺序展示，包含：
- 日期选择 + 顶部操作栏
- 快速添加区域 (`QuickNameLine`)
- "常用"快捷chips (`FrequentNameLines`)：显示最近14天出现次数最多的10个事件名
- 事件列表 (`LazyColumn`)：所有事件混合展示

问题：
1. "常用"区域是非待办事项，用户需要主动点击chips才能添加待办
2. 没有清晰地区分"已完成"和"待办"状态
3. 智能合并需要手动触发

## Goals / Non-Goals

**Goals:**
- 首页分两个区块：顶部已完成事件列表，底部今日待办列表
- "今日待办"由算法驱动，自动展示最可能需要做的事
- 支持同一事件同一天完成多次
- 智能合并成为默认行为，用户无感知

**Non-Goals:**
- 不改变现有数据模型（EventEntity 字段不变）
- 不改变时间记录逻辑（startTime/endTime/duration）
- 不引入"每日目标"或"打卡"概念
- 不改变统计页面和导出功能

## Decisions

### 1. 推荐算法：按总出现次数排序

**选择**：统计最近14天每个事件名称的**总出现次数**，取前5名

**理由**：
- 比"出现天数"更直观（用户关心的是"做了多少次"）
- 比"周频率"简单，无需计算平均值
- 5个固定数量，确保界面简洁

**替代考虑**：
- 按出现天数排序：可能推荐每天必做但频率不高的"复盘"类事项
- 按周频率排序：计算成本高，且结果差异不大

### 2. 推荐列表与事件的关系

**选择**：推荐名称只是"建议"，用户添加的实际事件独立存在

**数据流**：
```
推荐名称列表（算法生成）
    ↓ 用户点击或已有事件完成
实际 EventEntity 记录（独立存在）
```

**理由**：
- 推荐名称 ≠ 待办事项，它们是不同的概念
- 已完成的事件显示"再来一次"，点击创建新的 PENDING
- 未开始/进行中的事件显示在"今日待办"中

### 3. 再来一次的语义

**选择**：点击"再来一次"创建新的 PENDING 事件（不是直接开始）

**理由**：
- 创建新事件后，用户可以选择稍后再开始
- 保持一致性：所有事件都从 PENDING 开始
- 避免误触：用户明确知道自己在做什么

### 4. 智能合并触发时机

**选择**：在 `stopActiveEvent()` 执行时触发合并检查

**理由**：
- 时机合理：用户刚完成一件事，可能想继续做同类事项
- 不需要额外的定时器或后台任务
- 用户无感知，后台静默执行

**合并条件**：
- 结束的事件名称 == 当前 IN_PROGRESS 事件的名称
- 时间间隔 < 5分钟

### 5. 删除操作

**选择**：直接删除，无确认弹窗

**理由**：
- 简化操作流程
- Room 数据库支持软恢复（undo）可通过 Snackbar 实现
- 不影响数据安全（用户可在统计页面查看历史）

## Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|------|------|------|
| 推荐列表为空（历史数据不足5个） | 底部待办区域为空 | 降级为仅显示用户已添加的事件 |
| 推荐算法每次页面加载都执行 | 轻微性能开销 | 使用 Room Flow 缓存，定期刷新 |
| "再来一次"被频繁点击 | 同一事件堆积多条记录 | 保持现有逻辑，允许用户自行管理 |
